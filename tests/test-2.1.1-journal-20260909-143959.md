## Обнаруженные сбои

Уточнение среды: на Astra 1.6 зависание воспроизвелось и с локальным DEB.
`ps` показал `dpkg` в состоянии D / `autofs_wait`; `findmnt -t autofs`
показал автомонтирование `/parsecfs` через `systemd-1`. Поэтому зависание нельзя
объяснять только доступом к `/mnt/d`. Первая восстановительная переустановка
локального DEB завершилась rc=0; последующий повтор снова выявил проблему среды.

1. ALSE-1.7.9-UU1, ALSE-1.8.6, alse-1.8.5-mg16.3.0 и alse-1.8.3.uu1-mg15.8.4: `pg_restore` вернул 1 на `COPY schedule.at ...`: `relation "schedule.at" does not exist`. Перед этим расширение pgpro_scheduler создавалось. Это требует проверки совместимости версии расширения источника и назначения; данные расширения не выкидывались для получения формального успеха.
2. alse-1.8.2.uu1-mg15.7.0 и alse-1.8.4-mg16.3.0: `extension "pg_variables" is not available`; отсутствует pg_variables.control у Tantor. Требуется совместимый комплект расширений/сервера. Смена семейства автоматически не выполнялась.
3. Astra 1.6, дополнительная попытка: повторная установка mode 1 зависла при распаковке, остановлена timeout через 180 секунд, rc=124. dpkg --audit затем потребовал переустановить claster-creator. Итог восстановления состояния пакета записан ниже.
4. Первичная очистка Astra 1.8.6 через pg_dropcluster прерывалась при systemctl disable. Очистка завершена с `PG_CLUSTER_CONF_ROOT=/etc/postgresql` (штатная переменная postgresql-common), прямой остановкой кластера и удалением только его точных unit-файлов/ссылок.

## Выполненные фазы

Третья попытка Astra 1.6 дополнительно подтвердила повторную установку mode 4
и удаление кластера через `create-claster.sh --action delete ...
--backup-before-delete no` (rc=0). Mode 3 в этой попытке отклонил остаточный
`/etc/postgresql/16/qa55416m3/conf.d` от предыдущей штатной очистки; зависимый
port/move тест не нашёл кластер. Это дефект подготовки теста: `pg_dropcluster`
сохраняет пользовательские conf.d, а не дефект защитного отказа холодного рестори.
В финальной очистке точные каталоги конфигурации удалённых кластеров удаляются
после проверки пустого реестра и нормализованного пути.

На всех семи: удаление исходных кластеров, установка свежего mode 1, проверка пустого списка (имитационная), синтаксис/help/version, чтение man, неизвестный ключ, отказ административного вызова от nobody, создание QA-кластера, попытка восстановить указанный архив, финальная очистка.

На Astra 1.6 дополнительно: контрольные данные, hot/cold backup, рестори новой БД, отказ и разрешённое overwrite, ротация count/size, сборка mode 1–4, установка mode 2–4. Контрольная БД имеет checksum `57a63c0d2d3517bf733aaae36ed8387e`; она дополняет восстановленную asvd. Hot-тесты и mode 4 этой фазы используют контрольную БД, cold archive включает также восстановленную asvd.

На остальных шести зависимые фазы остановлены после неуспешного восстановления asvd. Исходные данные не подменялись контрольной БД для обхода сбоя.
