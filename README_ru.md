# pg_claster_creator

Управление кластерами PostgreSQL в Astra Linux и совместимых системах семейства Debian через интерактивные Bash-меню или командную строку. Сборка Debian-пакетов, устанавливающих инструменты и, при необходимости, разворачивающих кластер, восстанавливающих бэкап или инициализирующих БД из SQL.

**Версия:** 2.5.5 · **Язык:** [English](README.md) | Русский

Написание `claster` сохранено в именах проекта, команд и пакетов для совместимости. Интерактивные сообщения и вывод `--help` сейчас на русском; заголовки сценариев и MAN-страницы содержат документацию на английском.

## Возможности

| Инструмент | Назначение |
| --- | --- |
| `create-claster.sh` | Подготовка серверных пакетов; просмотр, создание, запуск/остановка, переименование, перемещение, бэкап, рестори и удаление кластеров; изменение портов и выполнение SQL. |
| `create-claster-backup.sh` | Горячие бэкапы БД, ротация по количеству или суммарному размеру, настройка заданий cron. |
| `create-claster-deb.sh` | Сборка DEB-пакетов только со сценариями либо с развёртыванием БД. |

Горячие бэкапы используют дампы PostgreSQL в формате custom. Холодные бэкапы содержат данные, конфигурацию и сведения о службе кластера. Оба вида включают метаданные исходного сервера. Каталоги бэкапов и доступные для чтения файлы бэкапов/SQL могут использоваться через символьные ссылки.

Кластер определяется **мажорной версией PostgreSQL и именем кластера**. Например, `17/demo` и `18/demo` — разные кластеры; их пути, службы и порты при этом не должны конфликтовать.

## Требования и выбор сервера

- Linux с APT, `dpkg-query` и systemd; Bash 4.4 или новее.
- Права root либо `sudo` для управления кластерами и выполнения плановых бэкапов.
- Настроенные APT-репозитории с `postgresql-common`, его зависимостями и нужными серверными пакетами. Доступ к репозиториям поставщиков обеспечивает администратор.
- GNU-утилиты, включая `tar`, `find`, `sort`, `sed` и `awk`.
- `flock` для сценария автоматического бэкапа; установленная и запущенная служба cron для заданий по расписанию.
- Для сборки DEB: `dpkg-deb` и `gzip`; при сборке на подключённой файловой системе Windows в WSL также требуется `fakeroot`.
- Указанная в конфиге локаль должна быть доступна на машине.

Проект рассчитан на Astra Linux 1.6, 1.7 и 1.8 и совместимые системы Debian/Ubuntu. В журналах проверок также представлен Linux Mint 22.3; это не гарантирует работу каждой комбинации ОС и сервера.

Поддерживаемые семейства пакетов в порядке автоматического выбора:

| Уровень приоритета | Семейство (`--pg-family`) | Серверный пакет |
| --- | --- | --- |
| 1 | `postgrespro-ent` | `postgrespro-ent-N-server` |
| 1 | `tantor-se` | `tantor-se-server-N` |
| 2 | `tantor-be` | `tantor-be-server-N` |
| 3 | `tantor-free` | `tantor-free-server-N` |
| 3 | `postgresql` | `postgresql-N` |

`N` — мажорная версия PostgreSQL. Внутри уровня более новые мажорные версии идут первыми; равные варианты сортируются по имени пакета. Tantor Free и ванильный PostgreSQL равноприоритетны. Также поддерживаются прежние имена `postgresql-N-server` и `tantor-free-server-N-server`.

Явный `--package` или подходящий установленный сервер, выбранный конфигурацией, имеет преимущество перед автоматическим ранжированием. Заголовок главного меню показывает выбранный пакет для **новых кластеров**, а не перечень всех установленных серверов. Для бэкапа сервер определяется по существующему кластеру и его бинарным файлам.

Postgres Pro требует соответствующий пакет `contrib`. Клиентские пакеты, пакеты разработки, расширения и неверсионированный метапакет `postgresql-contrib` не считаются серверами. Перед установкой серверных пакетов сценарий выполняет симуляцию транзакции APT и отклоняет план, удаляющий установленные пакеты.

## Быстрый старт

Выполняйте команды из локальной копии проекта в Linux либо по её пути, подключённому в WSL. Для запуска исходных сценариев скачанный DEB не требуется.

### 1. Подготовьте закрытый конфиг

Скопируйте поставляемый конфиг и перед запуском команд управления проверьте локаль, семейство/версию сервера, имена и пароли:

```bash
sudo install -d -m 0700 /etc/pgcc
sudo install -m 0600 ./.new-claster.config /etc/pgcc/site.config
sudoedit /etc/pgcc/site.config
```

Поставляемые учётные данные — примеры, а не пароли для продуктивной среды. Конфигурационные файлы исполняются как Bash-код: используйте только доверенные файлы.

### 2. Откройте меню управления

```bash
sudo bash ./create-claster.sh --config /etc/pgcc/site.config
```

Выберите **Кластер: Установить** для создания кластера либо другую операцию. При запуске могут устанавливаться недостающие зависимости и серверные пакеты; запуск программы не является проверкой состояния только для чтения.

### 3. Ознакомьтесь с интерфейсами

```bash
bash ./create-claster.sh --help
bash ./create-claster-backup.sh --help
bash ./create-claster-deb.sh --help
bash ./create-claster.sh --version
```

Запросы справки и версии не требуют прав root.

## Конфигурация

Все три сценария выбирают один конфигурационный файл в следующем порядке:

1. `--config FILE` или `--config=FILE`.
2. Непустая переменная `PGCC_CFG`.
3. Существующий `/usr/local/shared/pg_claster_creator/.new-claster.config`.
4. `.new-claster.config` рядом с разрешённым файлом сценария.

Явные относительные пути отсчитываются от каталога запуска. Отсутствующий или недоступный явно выбранный файл вызывает ошибку без перехода к запасному конфигу. Чтение и сохранение конфигурации используют один и тот же выбранный файл.

Приоритет поддерживаемых функциональных параметров: **CLI > непустая переменная окружения > конфиг/значение по умолчанию**. У справки и версии нет ENV-эквивалентов. Полное соответствие для каждого сценария приведено в `--help`, англоязычных заголовках и MAN-страницах.

| Поле конфигурации | Значение |
| --- | --- |
| `LANG`, `LC_ALL` | Локаль PostgreSQL и вспомогательных утилит. |
| `pg`, `pg_ver` | Семейство сервера и мажорная версия PostgreSQL по умолчанию. |
| `cls_pt`, `cls_nm` | Порт кластера и имя кластера/начальной БД по умолчанию. |
| `cls_ch` | Прикладная схема и роль-владелец БД. |
| `cls_us`, `cls_pw` | Прикладная роль входа и пароль для прикладной роли и роли-владельца. |
| `backup_dir` | Каталог хранения бэкапов и поиска бэкапов/SQL. |

Пять исходных параметров `cls_*` сохраняются при записи выбранного сервера или каталога бэкапов. Защищайте конфиг как секрет; при сохранении сценарий назначает ему права `0600`.

**`share` и `shared` — разные пути:** DEB устанавливает сценарии и поставляемый конфиг в `/usr/local/share/pg_claster_creator/`. Необязательный конфиг конкретной машины расположен в `/usr/local/shared/pg_claster_creator/` и автоматически не создаётся.

## Использование и автоматизация

### Доступность интерфейсов

| Операция | Интерактив | CLI / окружение |
| --- | --- | --- |
| Информация, создание, изменение порта/каталога данных, бэкап, рестори, удаление кластера | Да | `--action` / `PGCC_ACTION`: `info`, `install`, `port`, `move-data`, `backup`, `restore`, `delete` |
| Запуск/остановка и переименование кластера; SQL на существующей БД | Да | Только меню |
| Удаление отдельной БД | Да | Только меню; CLI `delete` удаляет кластер |
| Горячий бэкап и ротация через вспомогательный сценарий | Бэкап без запросов | Позиционные параметры цели либо ENV-параметры цели и ключи |
| Настройка задания бэкапа в cron | Да | `--cron` / `PGCC_CRON=yes` открывает диалог расписания |
| Сборка DEB в режимах 1–5 | Да | Укажите `--mode` и `--non-interactive` |

Выбор `--action` или `PGCC_ACTION` отключает меню и подтверждения. Отсутствие обязательных параметров вызывает ошибку; перед автоматизацией явно задавайте целевые объекты и проверяйте разрушающие опции.

### Команды управления кластером

Примеры предполагают существующие кластер `16/demo` и БД `demo`; замените версию, имена и пути на значения вашей машины:

```bash
# Список зарегистрированных кластеров; подготовка при запуске сохраняется.
sudo bash ./create-claster.sh --config /etc/pgcc/site.config --action info

# Бэкап одной БД без остановки её кластера.
sudo bash ./create-claster.sh --config /etc/pgcc/site.config \
  --action backup 16 demo --backup-type hot --database demo

# Холодный бэкап: при архивировании требуется остановка кластера.
sudo bash ./create-claster.sh --config /etc/pgcc/site.config \
  --action backup 16 demo --backup-type cold

# Изменение порта: операция может прервать обслуживание.
sudo bash ./create-claster.sh --config /etc/pgcc/site.config \
  --action port --pg-version 16 --cluster-name demo --port 5433
```

`--data-root /DATA` задаёт `/DATA/pg_N/CLUSTER` при создании или перемещении данных. Неинтерактивная установка при занятом порте выбирает следующий свободный и сообщает фактический порт; не предполагайте, что запрошенный порт сохранён.

Для выполнения SQL откройте **Изменить → Выполнить SQL**, выберите работающий кластер и БД, затем номер `.sql` или путь к файлу. Относительные пути ищутся от каталога запуска, затем от каталога бэкапов. Выполнение подтверждается только `y/Y`. SQL запускается от `postgres` через `psql -X` с `ON_ERROR_STOP`; это не делает произвольный сценарий транзакционным. В `create-claster.sh` нет входных параметров `--action sql` и `PGCC_SQL_FILE`.

### Ротация бэкапов и расписание

```bash
# После успешного бэкапа оставить семь новейших подходящих горячих архивов.
sudo bash ./create-claster-backup.sh --config /etc/pgcc/site.config \
  --backup-dir /srv/pg-backups/demo --files-cnt 7 16 demo demo
```

Для ограничения суммарного размера используйте `--files-size 10GiB` вместо `--files-cnt`; параметры взаимоисключающие. Ротация использует строгую маску имени с мажорной версией, БД и временем, а не содержимое архивов. Для разных кластеров с одноимёнными БД используйте отдельные каталоги. Как минимум новейший подходящий бэкап сохраняется, даже если он превышает лимит размера.

Позиционную цель `VERSION CLUSTER DATABASE` можно заменить одновременным заданием `PGCC_PG_VERSION`, `PGCC_CLUSTER_NAME` и `PGCC_DATABASE`. Переменные `PGCC_FILES_CNT`, `PGCC_FILES_SIZE` и `PGCC_BACKUP_DIR` соответствуют параметрам ротации и хранения. Добавьте `--cron` для настройки задания в `/etc/cron.d`; выбор расписания остаётся интерактивным. Блокировка задачи БД предотвращает её одновременные запуски.

## Сборка Debian-пакетов

Перед сборкой проверьте конфигурацию: **выбранный конфиг включается в DEB**. Не распространяйте случайно продуктивный пароль или закрытую конфигурацию машины.

Сборка пакета только со сценариями из копии проекта:

```bash
bash ./create-claster-deb.sh --config ./.new-claster.config \
  --mode 1 --non-interactive
```

Результат — `dist/claster-creator-2.5.5.deb`. Создаваемое содержимое `dist/` игнорируется Git. GitFlic CI и GitHub Actions проверяют и собирают пакет, сохраняют его как артефакт задания и публикуют DEB/контрольные суммы во вложениях релиза для соответствующих тегов `vX.Y.Z`. GitHub Actions использует облачный Ubuntu-агент и автоматический токен задания. Требования, защита релизов и границы проверки описаны в [CI и сборке релизов](CI.md) (на английском).

Установите этот пакет только со сценариями на машину с настроенными необходимыми репозиториями:

```bash
sudo apt install ./dist/claster-creator-2.5.5.deb
```

| Режим | Действие при установке пакета |
| --- | --- |
| 1 | Установить сценарии, конфигурацию, Markdown-документацию и MAN-страницы. |
| 2 | Установить инструменты и создать кластер. |
| 3 | Установить инструменты и восстановить встроенный холодный бэкап кластера. |
| 4 | Установить инструменты, создать кластер и восстановить встроенный горячий дамп БД. |
| 5 | Установить инструменты, создать кластер/БД и выполнить встроенный SQL-файл. |

Без режима сборщик открывает меню. В режимах 2–5 запросы включены по умолчанию; для автоматизации используйте `--non-interactive`. Режимы 3/4 требуют `--backup-file` соответствующего типа; режим 4 также требует `--database`. Режим 5 требует `--sql-file` / `PGCC_SQL_FILE` и `--database` / `PGCC_DATABASE`. Интерактивные списки фильтруют холодные/горячие бэкапы по режиму и предлагают выбор `.sql` в режиме 5. SQL должен быть самодостаточным: подключаемые внешние файлы не упаковываются.

При автоматическом выборе Postgres Pro в режимах 4/5 `--pg-version` задаёт **минимальную мажорную версию**: альтернативы contrib предпочитают 18, затем 17 и далее до этого минимума. Чтобы зафиксировать имя серверного пакета, задайте `--package`. Холодный режим сохраняет серверный пакет из метаданных бэкапа.

`--output-dir` меняет каталог результата; `--force` разрешает замену существующего DEB. Временные деревья сборки очищаются при выходе; родительский `tmp/` удаляется только если создан этим запуском и остался пуст. Оба архива DEB сжимаются gzip для совместимости со старыми версиями `dpkg` в Astra.

Каждый режим устанавливает все обычные файлы `*.md` из корня, включая оба README и текущий журнал, в `/usr/local/share/pg_claster_creator/`. Подкаталоги, например `tests/`, и символьные ссылки исключаются. Ссылки на основной и бэкап-сценарий создаются в `/usr/local/bin`; установленный сборщик запускается по полному пути. Английские и русские MAN-страницы устанавливаются в `/usr/share/man/`.

Режимы развёртывания используют промежуточные и итоговые маркеры в `/var/lib/claster-creator`. Перед повтором неудачного развёртывания прочтите MAN сборщика. В частности, `CLASTER_FORCE_INSTALL=1` при установке пакета удаляет целевой кластер **без бэкапа** перед повторным развёртыванием; `CLASTER_FORCE_DB_INSTALL=1` перезаписывает только целевую БД и поддерживается лишь в режиме 4. Флаги взаимоисключающие и не являются параметрами сборки. SQL режима 5 после ошибки автоматически не повторяется, поскольку частичные изменения уже могли сохраниться.

## Безопасность и эксплуатационные ограничения

- Холодный бэкап останавливает кластер на время архивирования. Изначально работавший кластер запускается после успеха; изначально остановленный может временно запускаться для сбора метаданных БД, затем снова останавливаться. После ошибок проверяйте состояние.
- Переименование, изменение порта/каталога данных, удаление и подготовка службы поставщика могут останавливать службы. Запросы остановки сопровождаются уведомлением, в том числе в автоматическом режиме; уведомления не являются дополнительными запросами подтверждения.
- Переименование сохраняет исходное состояние запуска, но не переименовывает БД, роли и внешние задания cron. При частичной ошибке создаётся файл состояния для восстановления, автоматического отката нет.
- Удаление кластера проверяет его остановку и удаляет проверенные пути конфигурации, данных и службы без `pg_dropcluster`. Внешние цели WAL/tablespace и общие либо нестандартные файлы могут сохраняться с предупреждением.
- Горячие бэкапы могут содержать хеши паролей ролей. Защищайте бэкапы, конфиги, встроенные данные развёртывания и генерируемые команды повторной сборки `create-claster-deb-last.sh`. Передача пароля через окружение исключает аргумент командной строки, но не заменяет хранилище секретов.
- Восстанавливайте только доверенные архивы и выполняйте только доверенный SQL. Холодный рестори назначает `/var/log/postgresql` владельца и группу `root:postgres` и права `1775`; права существующих файлов журналов не сбрасываются. Сброс WAL — аварийная операция с риском потери данных, а не штатная часть бэкапа.
- Планируйте свободное место и простой для физических бэкапов и перемещения данных. Проверяйте восстановление на изолированной машине до использования бэкапов в продуктивной среде.

## Особенности WSL

Храните PGDATA и критические каталоги кластера в Linux-файловой системе. Подключённый раздел Windows, например `/mnt/d`, может не обеспечивать POSIX-владельцев и права: защищайте архивы средствами контроля доступа Windows. Неподдерживаемое изменение прав не подтверждает прохождение проверки прав; ошибки чтения/записи архивов остаются ошибками.

WSL-специфичная обработка syslog-ng предназначена для функционального тестирования в WSL без `/dev/parsec`. Она заменяет только соответствующие штатному шаблону конфиги кластеров с неразрешёнными ссылками на PostgreSQL-парсеры Astra, сохраняет оригиналы и проверяет замену с откатом при ошибке. Замена собирает **исходный текст журналов, а не структурированные события аудита Astra**. Рабочие и пользовательские конфигурации сохраняются.

На обычных физических или виртуальных Linux-машинах этот механизм не задействован. Он не меняет глобальные настройки PARSEC и не выполняет автоматический reload/restart syslog-ng, а также не исправляет падения PID 1 или служебные вызовы пакетных установщиков. Перед изменением служб прочтите **WSL syslog-ng troubleshooting** в заголовке основного сценария.

После установки DEB используйте `man create-claster.sh`, `man create-claster-backup.sh` или `man create-claster-deb.sh`. Русские страницы можно выбрать командой `LANG=ru_RU.UTF-8 man create-claster.sh`, если локаль доступна.

Зафиксированный прогон 2.5.3 охватывает восемь WSL-дистрибутивов: 35 из 59 обязательных ID подтверждены полностью, у 24 остались непроверенные обязательные варианты. В выполненных проверках ошибок продукта не обнаружено; **это не полный результат passed**. Объём, причины пропусков и длительность приведены в журнале.

Полный прогон разрушителен: план может удалять кластеры и удалять/переустанавливать серверные пакеты. Используйте одноразовые стенды с явным разрешением на такие действия; следуйте разделу **Начало тестирования** в `TEST.md`, а не общей команде запуска тестов. Исторические локальные журналы находятся в игнорируемом `tests/` и не поставляются. Журнал в пакете подтверждает только заявленный объём проверок, а не сертификацию всех возможностей.
