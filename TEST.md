# Тестирование версии 1.0.0

## Среда проверки

Проверка выполнялась 4 сентября 2026 года в локальной WSL по умолчанию.

| Компонент | Значение |
|---|---|
| Дистрибутив | Astra Linux Special Edition 1.6 «Смоленск» |
| Обновление | Update 14, Bulletin 20231226SE16 |
| Архитектура | `x86_64` |
| Ядро WSL | `6.18.33.2-microsoft-standard-WSL2` |
| Bash | GNU Bash `4.4.12(1)-release` |
| Пакетная система | APT/dpkg |
| systemd | присутствует в тестовой WSL |

В WSL были подключены штатные репозитории Astra Linux и локальный файловый репозиторий PostgreSQL Pro.

## Выполненные проверки

### Синтаксис

- Выполнен разбор всего `create-claster.sh` командой `bash -n` внутри WSL.
- Ошибок синтаксиса Bash не обнаружено.
- Проверено, что файл можно подключить через `source` без автоматического запуска основного меню.

### Конфигурация

- Проверено чтение `.new-claster.config`.
- Проверены ожидаемые начальные значения семейства `postgresql`, версии `16` и каталога `/.postgres/backup`.
- Проверена совместимость синтаксиса конфига с Bash 4.4.

### Разбор и приоритет пакетов

Функциональными проверками подтверждён разбор следующих имён:

| Имя пакета | Ожидаемый результат |
|---|---|
| `postgrespro-ent-16-server` | семейство `postgrespro-ent`, версия `16` |
| `postgresql-15-server` | семейство `postgresql`, версия `15` |
| `tantor-free-server-17-server` | семейство `tantor-free`, версия `17` |
| `tantor-free-server-16` | совместимое имя Tantor, семейство `tantor-free`, версия `16` |

Проверено назначение приоритетов по версии PostgreSQL: самая новая версия получает приоритет `1`, следующая по убыванию — `2` и далее. Для нескольких серверных пакетов одной версии выводится одинаковый приоритет.

Проверено повторное отображение меню выбора пакета: после буквенного, пустого или выходящего за диапазон значения терминал очищается, выводится предупреждение и заново отображается полный сгруппированный список.

Также выполнен вызов поиска доступных пакетов через `apt-cache` и установленных пакетов через `dpkg-query`.

Для PostgreSQL Pro проверен обязательный комплект `postgrespro-ent-16-server` + `postgrespro-ent-16-contrib`. Пакет `contrib` содержит основной набор поставляемых расширений и совместим с установленным `postgresql-common`.

Проверен сценарий с русской локалью Astra Linux, где `apt-cache policy` выводит поле `Кандидат:` вместо `Candidate:`. Для машинного разбора команда принудительно запускается с `LC_ALL=C`; доступный `postgresql-common` версии `225astra3` корректно определяется как кандидат на установку.

Дополнительно проверена совместимость этого разбора с включённым `set -o pipefail`: обработчик `awk` читает вывод до конца и не завершает `apt-cache` сигналом `SIGPIPE` с кодом `141`.

### Управление vendor-службами

На уровне функций без изменения состояния systemd проверены:

- преобразование пакета `postgrespro-ent-16-server` в имя службы `postgrespro-ent-16`;
- преобразование пакета `tantor-free-server-16-server` в имя службы `tantor-free-server-16`;
- отсутствие вызовов `systemctl mask`;
- расположение вызова `systemctl unmask` перед `apt-get install` в функции установки.

При полном запуске сценария штатная служба `postgrespro-ent-16` была успешно остановлена, а её автозапуск отключён. Вызов `systemctl mask` не выполнялся.

### Полный запуск подготовки

В WSL выполнен реальный запуск подготовительной части сценария с выходом `0` из главного меню.

Подтверждено:

- установка обязательного `postgresql-common` версии `225astra3`;
- распознавание установленного комплекта `postgrespro-ent-16-server` и `postgrespro-ent-16-contrib` версии `16.2.2-1.smolensk`;
- совместимость комплекта `server + contrib` с `postgresql-common` по результату `apt-get -s`;
- остановка и отключение автозапуска `postgrespro-ent-16`;
- подготовка симлинков `/.postgres`;
- наличие ссылок `/.postgres/include -> /opt/pgpro/ent-16/include` и `/.postgres/run -> /var/run`;
- успешный переход в главное меню без создания кластера.

В ходе первого диагностического запуска до добавления защиты APT удалил конфликтующий метапакет `postgrespro-ent-16` при установке `postgresql-common`. Пакеты `postgrespro-ent-16-server`, `postgrespro-ent-16-client` и `postgrespro-ent-16-contrib` остались установленными. После этого в сценарий добавлена обязательная симуляция APT: если планируется удаление любого пакета, фактическая операция не начинается.

Каталог `/.postgres/data` уже существовал в WSL как обычный каталог с подкаталогом `subsys`. Сценарий корректно вывел предупреждение и не заменил его симлинком, сохранив существующие данные.

### PARSEC в WSL

Подтверждено отсутствие `/dev/parsec` и PARSEC-модуля в ядре `microsoft-standard-WSL2` при установленных пользовательских библиотеках PARSEC. Команда `pg_ctlcluster 16 subsys status` выводила предупреждение `Не удается открыть файл управления PARSEC.`, но возвращала код `0`; прямые `postgres`, `psql` и `pg_ctl` от пользователя `postgres` работали без предупреждения.

Проверен WSL-адаптер сценария: удаляется только точное известное предупреждение PARSEC, вывод `pg_ctlcluster` сохраняется, код завершения остаётся `0`. Произвольное сообщение stderr и ненулевой код тестовой команды проходят без изменений.

### Проверка вводимых имён

- Корректный идентификатор `subsys_2` принят.
- Имя `bad-name` с дефисом отклонено.

### Выбор кластера для удаления

На двух тестовых строках `pg_lsclusters` проверены отображение нумерованного списка, пункт `0 - Вернуться назад` и передача выбранной строки в обработчик удаления без скрытия вывода меню.

Проверено, что сценарий не содержит операции удаления общего каталога `/var/log/postgresql`. Удаление выполняется штатной утилитой `pg_dropcluster`, которая удаляет файл журнала выбранного кластера, но сохраняет общий каталог и журналы других кластеров.

### Главное меню и отдельный бэкап

Проверены новая нумерация главного меню (`3` — бэкап, `4` — рестори, `5` — удаление), выбор кластера в отдельном экране бэкапа и передача признака повторного запуска в функцию холодного архивирования.

### Параметры рестори

Проверены запросы целевого имени и порта, значения по умолчанию из метаданных бэкапа, обнаружение занятого порта и преобразование путей архива при восстановлении под новым именем.

Проверено обновление `external_pid_file` с исходного имени на целевое. В первом проблемном запуске PostgreSQL был `online`, но unit оставался `activating`, поскольку ожидал `/run/postgresql/16-subsys2.pid`, а сервер создавал `/run/postgresql/16-subsys.pid`.

При повторной проверке обычный `pg_ctlcluster 16 subsys2 start` от root зависал на перенаправлении в systemd, находившийся в состоянии `starting`. Прямой запуск `pg_ctlcluster --skip-systemctl-redirect 16 subsys2 start` завершился успешно: кластер перешёл в `online` и начал принимать подключения на порту `54322`. Для WSL сценарий переведён на этот режим; на штатной Astra Linux сохраняется совместная проверка кластера и systemd unit.

### Аргументы и переменные окружения

Без изменения реальных кластеров проверены:

- `-v` и `--version`, включая запуск без `root`;
- `-h` и `--help`, полнота перечня ключей, переменных и примеров;
- длинные параметры в формах `--key value` и `--key=value`;
- автоматическое включение неинтерактивного режима по `--action` и `PGCC_ACTION`;
- приоритет аргументов над `PGCC_*`, а `PGCC_*` — над значениями конфига;
- нормализация значений `yes/no`, включая `true/false`;
- отсутствие чтения stdin и очистки терминала в неинтерактивном режиме;
- выбор существующего кластера по точным версии и имени;
- отказ при отсутствии явно заданного имени цели для `backup/delete`;
- автоматический выбор точного серверного пакета;
- проверка параметров установки и вызов создания кластера на макете;
- безопасные значения по умолчанию: бэкап перед удалением включён, очистка WAL и перезапись при рестори отключены.

В реальной WSL от `root` выполнен `./create-claster.sh --action info`. Подтверждено, что при установленном `postgresql-common` вывод содержит только заголовок действия и таблицу `pg_lsclusters`. В выводе отсутствуют этап `Подготовка пакетов`, сообщения об уже установленных пакетах, команды отключения vendor-службы и уведомление о существующей ссылке данных. Состояние vendor-службы и структура `/.postgres` этим действием не изменялись.

Для действий `backup` и `delete` проверен позиционный синтаксис `ВЕРСИЯ КЛАСТЕР`, аналогичный `pg_ctlcluster`. Обе формы с аргументами `16 subsys` корректно нашли реальный кластер `16/subsys` в выводе `pg_lsclusters`; создание бэкапа и удаление не выполнялись. Проверены отказ при одном позиционном аргументе и отказ при смешивании с `--cluster-name`.

Для `--backup-file` в изолированном каталоге `tmp` проверено разрешение полного пути, относительного пути от текущего каталога, короткого имени относительно `backup_dir` и относительного пути с пробелом. Несуществующий файл корректно отклоняется. Распаковка и рестори при этой проверке не выполнялись.

### Сохранность параметров кластера

В отдельной копии сценария и конфига под каталогом `tmp` проверены:

- ввод недопустимого порта `aa` с последующим пустым вводом — применяется исходное корректное значение `5432`;
- проверяемое значение не заменяет значение по умолчанию до успешной валидации;
- изменение имени корректно задаёт временные значения по умолчанию для схемы, пользователя и пароля;
- отказ на итоговом подтверждении откатывает весь набор введённых значений;
- после изменения рабочих переменных и вызова служебного сохранения строки `cls_pt`, `cls_nm`, `cls_ch`, `cls_us`, `cls_pw` остаются равными исходным значениям из `.new-claster.config`;
- тест проводился на копиях, рабочий `.new-claster.config` не изменялся.

### Формат резервной копии

В изолированном временном каталоге `/tmp/create-claster.*` создан тестовый архив, соответствующий формату сценария.

Проверено:

- формирование имени архива `16-asvd-20260904-150059.tar.gz`;
- создание gzip-сжатого tar-архива;
- добавление префикса `root/`;
- ожидаемый путь `root/etc/postgresql/16/subsys/postgresql.conf`;
- наличие `root/backup-info.env`;
- извлечение и чтение метаданных без распаковки всего архива;
- наличие в метаданных имени хоста, типа и даты бэкапа, полной версии PostgreSQL, имени и порта исходного кластера;
- нумерованный перечень всех БД, включая `template0/template1`, с точными размерами в байтах и значениями `pg_size_pretty`;
- получение размера каталога данных командой `du -sh`, вывод пути и сохранение полей `data_directory_size_bytes`, `data_directory_size_pretty`, `data_directory_du_sh`;
- использование `backup_dir` как символьной ссылки на каталог при записи архива, построении списка рестори и разрешении короткого имени файла;

Проверено восстановление каталога данных через существующий симлинк: при ссылке `/var/lib/postgresql/16 -> /.postgres/data` архивный каталог `var/lib/postgresql/16/asvd` извлекается в `/.postgres/data/asvd`, а симлинк остаётся без изменения.

### Горячий бэкап и рестори

В изолированном каталоге `tmp` с макетами `pg_dump`, `pg_restore`, подключения и списка кластеров проверены:

- интерактивный выбор `1 — горячий` и передача введённого имени БД;

- формирование архива `16-sourcedb-20260905-101112-dmp.tar.gz`;
- наличие в горячем архиве дампа `16-sourcedb-20260905-101112-dmp.backup` и отдельного `backup-info.env`;
- запись в горячие метаданные исходного хоста, версии PostgreSQL, кластера, имени БД и её размера в байтах и формате `pg_size_pretty`;
- фактическая упаковка макетного горячего архива из дампа и `backup-info.env`;
- совместимость рестори со старыми горячими архивами без метафайла;
- использование custom-format `pg_dump` для работающего кластера;
- распознавание горячего архива по строгому имени;
- выбор целевого кластера и целевой БД;
- нумерованный вывод подключаемых пользовательских БД перед горячим бэкапом и рестори;

- преобразование введённого номера БД в имя соответствующей строки списка;

- числовое значение по умолчанию для существующей БД и его преобразование в имя при нажатии Enter;
- ввод нового имени БД при горячем рестори;
- выбор номера первой БД по умолчанию, когда БД с именем кластера отсутствует;
- создание отсутствующей целевой БД через версионную `createdb` до запуска `pg_restore`;
- извлечение ролей-владельцев из оглавления custom-format дампа;
- создание только отсутствующих прикладных ролей с административными атрибутами и паролем, равным имени роли;
- сохранение существующих и системных ролей без изменений;
- назначение найденной прикладной роли владельцем новой целевой БД;
- отсутствие параметра `--clean` при восстановлении в новую БД;
- отказ от восстановления в существующую БД без `overwrite=yes`;

- вызов `pg_restore` с очисткой существующих объектов и остановкой при ошибке;
- требование `overwrite=yes` для неинтерактивного горячего рестори;
- исключение постороннего `unrelated.tar.gz` из списка рестори;

Дополнительно в реальной WSL подтверждены обнаружение сокета `/tmp` для кластера `16/subsys`, выбор версионного каталога `/opt/pgpro/ent-16` и успешная проверка существования БД `subsys`. Реальные базы данных при проверке не изменялись. Фактический список из `/.postgres/backup` содержал только имя допустимого формата `16-subsys-20260905-085245.tar.gz`.

Тестовые вспомогательные файлы создавались в каталоге проекта `tmp` и были удалены после успешного прогона.

## Что не проверялось

Не выполнялись следующие потенциально разрушающие операции:

- фактическая переустановка серверных пакетов, поскольку `server` и `contrib` уже присутствовали;
- фактическая проверка `systemctl unmask` при новой установке сервера, поскольку служба уже не была замаскирована;
- создание настоящего PostgreSQL-кластера;
- изменение `pg_hba.conf` и `conf.d` действующего сервера;
- создание ролей, схемы и базы данных;
- создание, включение и запуск systemd unit;
- остановка, резервное копирование и удаление реального кластера;
- запуск `pg_resetwal` или `pg_resetxlog`;
- восстановление реального кластера поверх файловой системы.
- создание реального горячего дампа и применение `pg_restore` к реальной базе данных.

Полный сквозной тест необходимо выполнять на отдельной тестовой машине или WSL-экземпляре с подходящими репозиториями, установленным systemd и данными, которые допустимо удалить.

## Рекомендуемый приёмочный тест

Перед использованием в продуктивной среде рекомендуется:

1. Подключить те же репозитории, что будут использоваться на целевой системе.
2. Запустить сценарий на чистом тестовом экземпляре от `root`.
3. Проверить установку каждого необходимого семейства сервера отдельно.
4. Создать кластер с нестандартными именем и портом.
5. Проверить подключение, созданные роли, схему, параметры `pg_hba.conf` и автоматический запуск через systemd.
6. Добавить тестовые данные и выполнить удаление с холодным бэкапом без очистки WAL.
7. Восстановить кластер из архива и сравнить данные и конфигурацию.
8. Проверить повторный запуск сценария при уже установленных пакетах и нескольких кластерах.
9. Только на одноразовых тестовых данных отдельно проверить ветку с `pg_resetwal` или `pg_resetxlog`.
