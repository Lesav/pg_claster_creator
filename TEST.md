## Проверки patch-выпуска 2.1.3

Функциональность сценариев управления кластерами не изменена по сравнению с
2.1.2 (кроме отображаемого номера версии). Исходный
[журнал 2.1.2](TEST-2.1.2-journal-passed.md) полностью применим в своей области
проверок. Он включается в DEB 2.1.3 без изменения имени и содержимого.
Отдельно проверяются синтаксис/help/version, сборка пакета, его версия,
путь журнала, права 0644 и совпадение содержимого. Полный прогон WSL не повторялся.

Проверка упаковки 2.1.3 выполнена: все перечисленные проверки OK; конфиг внутри
DEB совпал с файлом проекта; отсутствие журнала отклоняется во всех modes 1–4.
Пакет собран во временном каталоге Linux и сохранён в `dist`: прямая сборка на
DrvFS давала недопустимые права `777` каталога DEBIAN. Предупреждение Ubuntu об
отсутствующей ru_RU.utf8 не препятствовало сборке; установка пакета не выполнялась.

## Проверки patch-выпуска 2.1.2

Обновлены версии трёх сценариев, README и шести man-страниц. Приоритет конфигурации:
`/usr/local/shared/pg_claster_creator/.new-claster.config`, затем файл рядом с
разрешённым сценарием. Для параллельных WSL необходим отдельный локальный конфиг;
общий файл проекта не должен изменяться.

Версия 2.1.2 проверена на семи Astra WSL:
[успешный журнал 2.1.2](TEST-2.1.2-journal-passed.md).
Все 105 фаз заданного SQL-сценария получили OK: создание asvd из SQL,
горячий/холодный бэкапы через ссылку, смена порта, перенос в /DATA,
очистка кластеров и каталогов /DATA и /BACKUP. Старые бэкапы предварительно сохранены.
Это не полный расширенный план: восстановление архивов и установка DEB
в этот прогон не входили. Общий конфиг проекта не изменился.
Итоговый журнал хранится в корне репозитория; каталог tests/ исключён из Git.

Проверка номера выпуска: `bash -n`, `--version` и `--help` для трёх сценариев;
mode 1 собирается как `claster-creator-2.1.2.deb` при запуске сборщика абсолютным
путём. Сборка через `bash create-claster-deb.sh` без `./` выявила ограничение
повторного вызова через fakeroot; используйте абсолютный путь или `./create-claster-deb.sh`.

### PARSEC в WSL

Подтверждено отсутствие `/dev/parsec` и PARSEC-модуля в ядре `microsoft-standard-WSL2` при установленных пользовательских библиотеках PARSEC. Команда `pg_ctlcluster 16 subsys status` выводила предупреждение `Не удается открыть файл управления PARSEC.`, но возвращала код `0`; прямые `postgres`, `psql` и `pg_ctl` от пользователя `postgres` работали без предупреждения.

Проверен WSL-адаптер сценария: удаляется только точное известное предупреждение PARSEC, вывод `pg_ctlcluster` сохраняется, код завершения остаётся `0`. Произвольное сообщение stderr и ненулевой код тестовой команды проходят без изменений.

### Интерактивное удаление

На двух тестовых строках `pg_lsclusters` проверены отображение нумерованного списка, пункт `0 - Вернуться назад` и передача выбранной строки в обработчик удаления без скрытия вывода меню.

В псевдотерминале проверено сохранение цветовой схемы в нумерованных списках: строка `online` получила ANSI-код зелёного цвета `32`, строка `down` — красного `31`, после каждой строки выведен сброс цвета. При перенаправлении вывода ANSI-коды отсутствуют, поэтому автоматический разбор не изменился.

Проверено, что сценарий не содержит операции удаления общего каталога `/var/log/postgresql`. Удаление выполняется штатной утилитой `pg_dropcluster`, которая удаляет файл журнала выбранного кластера, но сохраняет общий каталог и журналы других кластеров.

В изолированных каталогах внутри `tmp` дополнительно проверены:

- явное удаление оставшегося непустого каталога данных после макета успешного `pg_dropcluster`;
- вызов очистки каталога конфигурации `/etc/postgresql/{версия}/{кластер}` и каталога данных из выбранной строки;
- сохранение родительских каталогов;
- отказ от небезопасной цели `/testcluster`, родителем которой является корень файловой системы;
- вызов очистки systemd-файлов только с точными версией и именем выбранного кластера;
- успешное завершение, когда каталог конфигурации уже удалён штатной утилитой.

Реальные кластеры и их каталоги в этом тесте не удалялись.

Для режима удаления БД проверены:

- обязательное предложение горячего бэкапа выбранной БД с положительным ответом по умолчанию;
- передача версии, кластера, порта, каталога данных и выбранной БД в `make_hot_backup` до удаления;
- отдельное подтверждение удаления без резервной копии при отказе от горячего бэкапа;
- нумерованный выбор `1 — кластер`, `2 — база данных`, `0 — назад`;
- последовательный выбор кластера и второй БД из показанного списка;
- передача имени `asvd-old`, а не номера `2`, в обработчик удаления;
- вызов версионной `dropdb --force` через сокет и порт выбранного кластера;
- подтверждение удаления с отрицательным ответом по умолчанию;
- запрет удаления служебной БД `postgres`;
- сохранение прежнего удаления кластера при выборе режима `1` и в неинтерактивном действии `delete`.

В реальной WSL выполнен безопасный проход `Удаление → База данных → 16/subsys`: показан список `asvd`, `asvd-old`, `postgres`, `subsys` с размерами. Выбран пункт `0`; фактическое удаление БД не выполнялось.

### Параметры рестори

Проверены запросы целевого имени и порта, значения по умолчанию из метаданных бэкапа, обнаружение занятого порта и преобразование путей архива при восстановлении под новым именем.

Для защиты холодного рестори дополнительно проверены:

- обнаружение уже зарегистрированного целевого кластера;
- обнаружение оставшегося каталога `/etc/postgresql/16/asvd` после незавершённого прежнего рестори, даже когда кластер уже отсутствует в `pg_lsclusters`;
- вывод `АЛАРМ` и повторный запрос имени до запроса порта;
- принятие следующего свободного имени;
- повторная проверка непосредственно перед распаковкой;
- определение фактического unit `/lib/systemd/system/postgresql@16-subsys.service`, несмотря на устаревший путь `/usr/lib/systemd/system/...` в старом архиве;
- формирование нового unit с изменёнными именем кластера, каталогом данных и PID-файлом для старого архива без unit.

Файлы реального кластера и содержимое старого архива при этой проверке не изменялись.

Дополнительно выполнен реальный интерактивный проход со старым архивом `16-subsys-20260905-085245.tar.gz`: конфликтующее имя `asvd` отклонено из-за существующего `/etc/postgresql/16/asvd`, после чего принято свободное имя `codex_restore_unused`. Операция отменена на итоговом подтверждении, поэтому архив не распаковывался и кластер не создавался.

Проверено обновление `external_pid_file` с исходного имени на целевое. В первом проблемном запуске PostgreSQL был `online`, но unit оставался `activating`, поскольку ожидал `/run/postgresql/16-subsys2.pid`, а сервер создавал `/run/postgresql/16-subsys.pid`.

При повторной проверке обычный `pg_ctlcluster 16 subsys2 start` от root зависал на перенаправлении в systemd, находившийся в состоянии `starting`. Прямой запуск `pg_ctlcluster --skip-systemctl-redirect 16 subsys2 start` завершился успешно: кластер перешёл в `online` и начал принимать подключения на порту `54322`. Для WSL сценарий переведён на этот режим; на штатной Astra Linux сохраняется совместная проверка кластера и systemd unit.

## План полного тестирования

Этот раздел предназначен для независимого тестировщика и является обязательным
регрессионным планом для трёх сценариев:

- `create-claster.sh`;
- `create-claster-backup.sh`;
- `create-claster-deb.sh`.

Проверки выполняются на отдельной тестовой WSL/виртуальной машине. Использовать
продуктивные кластеры, единственную копию данных или каталоги с нужными файлами
запрещено. Перед началом следует сделать снимок тестовой системы, а перед
разрушающими проверками — убедиться, что восстановление снимка действительно
работает.

### Обязательный журнал тестирования

Тестировщик обязан вести отдельный журнал, например
`test-journal-YYYYMMDD-hhmmss.md`. Для каждого пункта этого плана в журнале
обязательно указываются его идентификатор, полное имя и результат. Пункт нельзя
пропускать молча: невыполненная проверка получает состояние `BLOCKED` или
`SKIPPED` с объяснением причины.

Допустимые состояния:

- `PASS` — фактический результат полностью совпал с ожидаемым;
- `FAIL` — найдено любое расхождение, зависание, необработанная ошибка или потеря данных;
- `BLOCKED` — проверка невозможна из-за состояния стенда или отсутствующей зависимости;
- `SKIPPED` — проверка исключена ответственным лицом с записанным обоснованием.

Рекомендуемый шаблон записи:

```markdown
### PT-CC-08 — Горячий бэкап существующей БД

- Дата и время: 2026-09-06 19:30 MSK
- Версия/коммит: 2.1.1 / <git commit>
- Стенд: B24749, Astra Linux SE 1.6, WSL2
- Предусловия: кластер 16/qa_src online, БД qa_db
- Команда и интерактивный ввод: <полная команда и ответы>
- Ожидаемый результат: <из соответствующего пункта плана>
- Фактический результат: <наблюдавшийся результат>
- Результат: PASS | FAIL | BLOCKED | SKIPPED
- Артефакты: <пути к полному логу, архиву, метафайлу, снимкам>
- Очистка после теста: выполнена | не выполнена, причина
- Комментарий/дефект: <номер дефекта или пояснение>
```

Для команд, создающих большой вывод (`apt`, `pg_dump`, `pg_restore`, `dpkg`),
в журнал прикладывается полный журнал stdout/stderr, а не только последние
строки. Секреты и открытые пароли перед публикацией журнала маскируются. Хеши
паролей из метаданных также считаются конфиденциальными. После каждого пункта
фиксируются `echo $?`, `pg_lsclusters`, состояние относящихся к тесту служб и
перечень созданных файлов. Время начала и окончания позволяет обнаруживать
зависания и нарушение заявленных тайм-аутов.

### Подготовка источника тестовых данных

Основой испытаний должен быть уже установленный работающий кластер. Если такого
кластера на стенде нет, тестировщик восстанавливает исходный кластер из
предоставленного холодного архива под временным именем и на свободном порту.
Разрушающие проверки никогда не выполняются над единственным исходным кластером:
сначала создаётся проверенный холодный бэкап или снимок WSL.

В журнале вводятся и далее последовательно используются обозначения:

```text
SRC_VER       — версия исходного PostgreSQL
SRC_CLUSTER   — существующий исходный кластер
SRC_PORT      — порт исходного кластера
SRC_DB        — существующая пользовательская БД
QA_CLUSTER    — временный тестовый кластер
QA_PORT       — свободный тестовый порт
QA_DB         — временная тестовая БД
QA_ROOT       — отдельный корень данных, например /DATA/pgcc-test
QA_BACKUP     — отдельный каталог бэкапов
```

В `SRC_DB` необходимо подготовить контрольный набор: таблицы с данными, sequence,
view, materialized view, функции, триггеры, внешние ключи, наследуемую таблицу с
унаследованным ограничением, объект с владельцем, отличным от владельца БД, и
ACL для ролей с `LOGIN` и `NOLOGIN`. Желательно установить хотя бы одно
доступное расширение из `contrib`. До бэкапов фиксируются список объектов,
владельцы, ACL, расширения, количество строк и контрольные суммы тестовых данных.

Ожидаемый результат: создаются data-каталог, конфигурация, `conf.d`, HBA,
версионный systemd unit, БД, схема, роли и `cron_user`; кластер online и доступен
на выбранном порту; custom path равен `QA_ROOT/pg_SRC_VER/QA_CLUSTER` и
отсутствующие каталоги создаются; отмена не оставляет частичной установки.

#### PT-CC-07 — Роли, настройки и расширения нового кластера

Действия: проверить владельцев БД/схемы, вход прикладной ролью, пароль,
`search_path`, `lc_messages`, HBA, `password_encryption`,
`shared_preload_libraries` и доступные расширения.

Ожидаемый результат: роли и владельцы соответствуют введённым данным; пароль
работает; для версии выше 16 применяется SCRAM, иначе MD5; в preload попадают
только существующие библиотеки; рестарт кластера проходит успешно.

#### PT-CC-08 — Конфликты имени, каталога и порта при установке

Действия: повторить имя существующего кластера, указать непустой data-каталог,
порт другого кластера и порт стороннего TCP-процесса. Проверить интерактив и
неинтерактивный `install` отдельно.

Ожидаемый результат: имя и каталог всегда отклоняются без повреждения данных;
интерактив повторно спрашивает порт; неинтерактивный режим выбирает первый
следующий свободный порт, создаёт кластер, выводит фактический порт и команду
`create-claster.sh --action port`.

#### PT-CC-09 — Переключение порта

Действия: выбрать online- и down-кластер, проверить текущий, недопустимый,
занятый другим кластером/процессом и свободный порт; повторить через `--action
port` и переменные `PGCC_*`.

Ожидаемый результат: опасные значения отклоняются; настройки согласованы в
`postgresql.conf`, `conf.d` и `postgresql.auto.conf`; online-кластер
останавливается и снова запускается, down-кластер остаётся down; подключение
возможно только на новом порту.

#### PT-CC-10 — Перемещение данных

Действия: переместить копию исходного кластера в `QA_ROOT`, затем вернуть в
дефолтное размещение; проверить отсутствующий root, пустую/непустую цель,
симлинк и попытку перемещения внутрь исходного каталога.

Ожидаемый результат: отсутствующий root и `pg_SRC_VER` создаются; данные и все
ссылки конфигурации/unit обновлены; состояние online/down сохраняется; контрольные
суммы данных не изменены; небезопасные цели отклоняются до перемещения.

### `create-claster.sh`: резервное копирование

#### PT-CC-11 — Интерактивный выбор горячего бэкапа

Действия: выбрать кластер номером, затем БД номером и именем; проверить
выравнивание имён разной длины и размеров.

Ожидаемый результат: показываются только БД выбранного кластера, выбор номером и
точным именем указывает одну и ту же БД, столбцы имени/размера выровнены; поле
размера имеет ширину девять символов и никогда не округляется до `1000.00` в
текущей единице.

#### PT-CC-12 — Горячий бэкап существующей БД

Действия: создать горячий бэкап `SRC_DB` в обычный каталог и через симлинк
`/.postgres/backup`; проверить архив и `backup-info.env`.

Ожидаемый результат: имя соответствует
`SRC_VER-SRC_DB-YYYYMMDD-hhmmss-dmp.tar.gz`, внутри находятся `.backup` и
метафайл; архив имеет режим `0600` либо выдаёт предупреждение FS; метаданные
содержат хост, время, семейство/версию/пакет, кластер/порт/data path, имя и размер
БД, роли, их атрибуты и доступные хеши, а также закомментированную команду сборки
DEB режима 4. Дамп читается `pg_restore --list`.

#### PT-CC-13 — Холодный бэкап кластера

Действия: создать холодный архив online-кластера, затем изначально down-кластера;
проверить вариант без очистки WAL. В отдельной одноразовой копии проверить
подтверждённую очистку WAL штатной версионной командой.

Ожидаемый результат: имя соответствует
`SRC_VER-SRC_CLUSTER-YYYYMMDD-hhmmss.tar.gz`; размер, полученный через `du`,
выводится в нормализованном девятисимвольном поле; метафайл
содержит размер data-каталога, полный список БД и их размеры, пути, пакет, unit и
команду DEB режима 3; архив содержит только конфигурацию выбранного кластера,
его data, его log-файл и unit, разыменовывая нужные ссылки. Общий каталог логов и
логи других кластеров не копируются как цель удаления. Исходное состояние
online/down восстанавливается.

#### PT-CC-14 — Отказ бэкапа

Действия: смоделировать недоступный каталог, нехватку места, ошибку `pg_dump`,
ошибку остановки/старта и повреждённый архив.

Ожидаемый результат: код ненулевой, неполный итоговый архив не выдаётся за
успешный, исходный кластер по возможности возвращён в исходное состояние,
причина однозначно присутствует в журнале.

### `create-claster.sh`: восстановление и удаление

#### PT-CC-15 — Фильтрация и путь к архиву

Действия: поместить в каталог корректные горячие/холодные имена и посторонние
`.tar.gz`; проверить интерактивный список, относительный путь и полный путь
`--backup-file`.

Ожидаемый результат: список содержит только две поддерживаемые маски; тип
определяется правильно; относительный и абсолютный путь восстанавливают один и
тот же архив; отсутствующий/повреждённый файл отклоняется.

#### PT-CC-16 — Горячий рестори в новую БД

Действия: выбрать целевой кластер и новую БД; восстановить горячий архив с
ролями/ACL/расширением.

Ожидаемый результат: отсутствующая БД и отсутствующие роли создаются; доступные
хеши паролей применяются; владельцы и ACL восстановлены; количества строк,
контрольные суммы и перечень объектов совпадают с источником.

#### PT-CC-17 — Горячий рестори поверх существующей БД

Действия: предварительно изменить данные целевой БД; проверить отказ по
умолчанию, затем `--overwrite yes`. В архиве должна присутствовать наследуемая
таблица с наследуемым ограничением.

Ожидаемый результат: без разрешения БД не меняется; при разрешении служебные БД
защищены, пользовательская БД удаляется целиком, создаётся с прежним владельцем
и восстанавливается без ошибки `cannot drop inherited constraint`; старые
объекты исчезают, данные и ACL совпадают с источником.

#### PT-CC-18 — Холодный рестори

Действия: восстановить архив под исходным и другим именем, на другом порту, в
дефолтный и custom data-root; отдельно проверить старый архив без unit.

Ожидаемый результат: конфигурация/data/log/unit согласованы с новым именем и
портом; целевой каталог помещается внутрь существующего симлинка каталога версии,
а не заменяет его; отсутствующий unit создаётся; кластер запускается без
зависания PARSEC/WSL; все БД и контрольные данные совпадают с метафайлом.

#### PT-CC-19 — Конфликты холодного рестори

Действия: указать имя зарегистрированного кластера, оставшийся каталог
`/etc/postgresql`, существующий data-каталог, unit и занятый порт.

Ожидаемый результат: до распаковки выводится аларм и требуется другое имя/порт;
существующие конфигурация, data и unit не изменяются и не затираются.

#### PT-CC-20 — Удаление БД

Действия: выбрать кластер и БД номером; согласиться с горячим бэкапом, затем
повторить с отказом. Проверить защиту `postgres`, `template0`, `template1`.

Ожидаемый результат: перед удалением всегда предлагается горячий бэкап с
положительным ответом по умолчанию; отказ требует отдельного подтверждения;
после успешного бэкапа БД удаляется; другие БД, роли и логи кластеров сохранены;
служебные БД удалить нельзя.

#### PT-CC-21 — Удаление кластера

Действия: удалить временный кластер с холодным бэкапом и без него; проверить
директории, unit, ссылки, log-файл и общий log-каталог.

Ожидаемый результат: холодный бэкап предлагается всегда и по умолчанию включён;
удаляются регистрация кластера, его конфигурация, data, unit, сохранённый unit и
только его log-файл. `/var/log/postgresql` и логи других кластеров остаются.

#### PT-CC-22 — CLI, ENV и позиционные аргументы

Действия: для каждого действия повторить обязательный позитивный тест через
ключи и через `PGCC_*`; проверить приоритет `CLI > ENV > config`, формы `backup
SRC_VER SRC_CLUSTER` и `delete SRC_VER SRC_CLUSTER`, недостающие/лишние аргументы.

Ожидаемый результат: интерактив отсутствует при полном наборе параметров;
приоритет соблюдён; позиционная адресация эквивалентна именованной; ошибка ввода
возникает до изменения системы.

#### PT-CC-23 — WSL, PARSEC и тайм-ауты

Действия: запустить start/stop/restore в целевой Astra WSL, где возможно
сообщение PARSEC; зафиксировать длительность. Смоделировать зависший systemctl.

Ожидаемый результат: сообщение PARSEC не вызывает бесконечного ожидания;
используется `--skip-systemctl-redirect`, фактический online/down подтверждается
через `pg_lsclusters`, а зависшая операция завершается предусмотренным тайм-аутом.

### `create-claster-backup.sh`

#### PT-BK-01 — Аргументы и валидация

Действия: проверить `<версия> <кластер> <БД>`, перестановку ключей,
`--backup-dir`, неизвестный ключ, отсутствующий аргумент, неверные размеры,
нулевые лимиты и одновременные `--files-cnt`/`--files-size`.

Ожидаемый результат: допустимые формы запускают бэкап; некорректные завершаются
до `pg_dump`; два лимита взаимоисключающие; все единицы B–TiB разбираются верно.

#### PT-BK-02 — Одиночный плановый горячий бэкап

Действия: создать бэкап `SRC_DB` в дефолтный и пользовательский каталог.

Ожидаемый результат: вызывается неинтерактивный горячий бэкап основного
сценария; имя, содержимое, метаданные и данные соответствуют `PT-CC-12`;
возвращается код `0` только после появления исправного архива.

#### PT-BK-03 — Ротация по количеству

Действия: создать больше архивов одной задачи, чем `--files-cnt`; рядом положить
архивы другой версии/БД и посторонние файлы. Для одноимённой БД той же версии из
другого кластера использовать отдельный `--backup-dir`.

Ожидаемый результат: после успешного нового бэкапа остаётся заданное число самых
новых файлов подходящей маски и минимум один файл; файлы других версий/БД,
посторонние файлы и отдельный каталог соседнего кластера не затрагиваются;
архивы не распаковываются для ротации.

#### PT-BK-04 — Ротация по размеру

Действия: создать набор архивов больше `--files-size`, включая один архив,
который сам превышает лимит.

Ожидаемый результат: старые подходящие файлы удаляются до соблюдения лимита, но
самый новый сохраняется всегда; другие маски не затрагиваются.

#### PT-BK-05 — Ошибка бэкапа и блокировка

Действия: смоделировать ошибку основного сценария и два одновременных запуска.

Ожидаемый результат: после неуспешного бэкапа ротация не выполняется; второй
параллельный процесс не создаёт конкурирующий архив и сообщает о блокировке.

#### PT-BK-06 — Создание cron-задачи

Действия: запустить `--cron` с каждым видом лимита и без лимита, ввести типовые
расписания, неверные значения и повторно создать ту же задачу.

Ожидаемый результат: периодичность и недостающий лимит запрашиваются
интерактивно; файл `/etc/cron.d/pg-claster-backup-*` создаётся/атомарно
заменяется с корректными правами, абсолютными путями и отдельным логом; команда
из cron выполняется без TTY и создаёт валидный архив.

### `create-claster-deb.sh`: сборка

#### PT-DEB-01 — Интерактивный выбор режимов

Действия: запустить без ключей, пройти режимы 1–4, неверный ввод и отмену;
отдельно явно вызвать `--mode 1`. В режимах 3 и 4 подготовить архивы разного
размера от килобайт до гигабайт и проверить строки общего списка.

Ожидаемый результат: без `--mode` показывается нумерованное меню; режимы 2–4
уточняют параметры и архив; отмена не оставляет DEB; явный mode 1 собирается без
чтения stdin. В списке архивов типы и размеры выровнены, размер содержит две
цифры после точки, двухбуквенную единицу и занимает не более девяти символов;
для показа списка архивы не распаковываются.

#### PT-DEB-02 — Неинтерактивная валидация

Действия: для режимов 2–4 собрать пакет полным набором ключей; затем убрать по
одному обязательному ключу, передать неправильный тип/версию архива,
относительный и абсолютный путь.

Ожидаемый результат: полный набор не вызывает запросов; относительный и полный
пути работают; неполный или противоречивый набор отклоняется до создания DEB.

#### PT-DEB-03 — Режим 1 и содержимое пакета

Действия: собрать mode 1, проверить `dpkg-deb --info/--contents`, права,
владельцев, man и установку/повторную установку.

Ожидаемый результат: пакет содержит конфиг, Markdown, три сценария и шесть
сжатых man-страниц в документированных путях; ссылки создаются только для
`create-claster.sh` и `create-claster-backup.sh`; сборщик установлен в `share`
без ссылки в `bin`; `Depends: postgresql-common`; Maintainer/Author корректны.

#### PT-DEB-04 — Имена пакетов и скелет

Действия: собрать все четыре режима, проверить имена, каталог `dist`, временный
скелет в `tmp`, `--output-dir` и защиту результата без/с `--force`.

Ожидаемый результат: имена соответствуют документированным шаблонам; скелет
создаётся заново и удаляется после сборки/ошибки; существующий DEB без `--force`
не перезаписывается.

#### PT-DEB-05 — Зависимости PostgreSQL Pro

Действия: mode 4 без `--package` с минимумом 16 и 14, с доступными версиями
16–18; проверить `Depends` и симуляцию `apt`. Повторить с явным `--package`.
Собрать mode 3 из холодного бэкапа PostgreSQL Pro 16.

Ожидаемый результат: автоматический минимум 16 даёт только
`postgresql-common, postgrespro-ent-18-contrib | postgrespro-ent-17-contrib |
postgrespro-ent-16-contrib`; каждый contrib подтягивает server той же версии;
APT выбирает самый новый доступный комплект не ниже минимума. Явный package
фиксирует точные server+contrib и отключает повышение. Холодный mode 3 содержит
ровно `postgresql-common, postgrespro-ent-16-server`, не добавляет `contrib` и
не допускает повышения основной версии физического бэкапа.

#### PT-DEB-06 — Дополнительные зависимости

Действия: повторить `--depends`, передать список через запятую, дубликаты,
недопустимое имя и покрытый `postgrespro-ent-16-server`; применить ключ в mode 1.

Ожидаемый результат: допустимые уникальные пакеты добавлены один раз; покрытый
server удалён с предупреждением; условия версий/небезопасные строки отклонены;
mode 1 не принимает дополнительные зависимости.

#### PT-DEB-07 — `create-claster-deb-last.sh`

Действия: подтвердить интерактивную сборку в доступном для записи каталоге и в
каталоге без права записи; проверить mode 1 и mode 4; повторить неинтерактивно.

Ожидаемый результат: файл создаётся только интерактивом, обычно рядом со
сборщиком, иначе в создаваемом `~/tmp`; запрашиваются права `0755`; команда
содержит абсолютные пути, все параметры, `--non-interactive` и `--force` и
успешно повторяет сборку. Неинтерактивный запуск файл не меняет. Пароль mode 2/4
защищён правами каталога/файла и отмечен предупреждением.

### `create-claster-deb.sh`: установка и `postinst`

#### PT-DEB-08 — Установка mode 2

Действия: установить через `apt install ./пакет.deb` на чистом снимке; повторить
с занятым запрошенным портом.

Ожидаемый результат: зависимости загружены, пустой кластер создан. При конфликте
выбран свободный порт; предупреждение и команда его смены повторены в самом
конце `postinst`; `dpkg` завершает настройку пакета с кодом `0`.

#### PT-DEB-09 — Установка mode 3

Действия: установить пакет с холодным архивом на чистом снимке, проверить
изменённые имя/порт/data-root; затем повторить при существующем целевом кластере.

Ожидаемый результат: кластер и все данные восстановлены; встроенный архив/план
имеют права `0600`; существующий кластер не затирается, выводится предупреждение,
а `postinst` завершается без ошибки.

#### PT-DEB-10 — Установка mode 4

Действия: установить пакет с горячим архивом на чистом снимке и с занятым
запрошенным портом; сохранить полный длинный вывод `pg_restore`.

Ожидаемый результат: выбран фактически установленный сервер допустимой версии,
созданы кластер, роли и БД, данные/ACL совпадают с источником; уведомление о
замене порта повторяется после строки успешного горячего рестори и остаётся в
конце журнала; пакет настроен успешно.

#### PT-DEB-11 — Идемпотентность и маркеры

Действия: повторно настроить пакет, удалить целевой кластер при оставшемся
`.done`, прервать mode 3/4 после `.cluster-created` и запустить снова.

Ожидаемый результат: завершённый план повторно данные не разворачивает;
устаревшие `.done/.cluster-created/.data-moved` сбрасываются при отсутствии
кластера; прерванный план продолжает нужный этап; `.done` появляется только
после фактической проверки кластера.

#### PT-DEB-12 — Существующий кластер без force

Действия: установить mode 2/3/4 при уже зарегистрированном целевом кластере без
принудительных флагов.

Ожидаемый результат: кластер и БД не меняются; выводится предупреждение;
`postinst` и пакет завершаются с кодом `0`, а не переводят dpkg в broken state.

#### PT-DEB-13 — `CLASTER_FORCE_INSTALL`

Действия: для mode 2, 3 и 4 установить пакет поверх тестового кластера с
`CLASTER_FORCE_INSTALL=1`.

Ожидаемый результат: существующий кластер удалён без бэкапа, маркеры сброшены,
полный план выполнен заново; данные результата соответствуют типу пакета.

#### PT-DEB-14 — `CLASTER_FORCE_DB_INSTALL`

Действия: изменить целевую БД и установить mode 4 с
`CLASTER_FORCE_DB_INSTALL=1`; повторить для mode 3 и одновременно с
`CLASTER_FORCE_INSTALL=1`.

Ожидаемый результат: в mode 4 кластер сохраняется, только БД пересоздаётся из
дампа; для холодного пакета флаг отклоняется до изменений; два force-флага
вместе отклоняются.

#### PT-DEB-15 — Создание data-root при установке

Действия: удалить весь заданный тестовый `QA_ROOT`, затем установить mode 2/4 с
`--data-root QA_ROOT`.

Ожидаемый результат: root, `pg_SRC_VER` и каталог кластера создаются; кластер
использует ожидаемый путь; соседние каталоги не изменяются.

#### PT-DEB-16 — Установка зависимостей через APT

Действия: на чистом снимке установить локальный mode 4 через `apt install
./пакет.deb`; отдельно зафиксировать ожидаемое ограничение прямого `dpkg -i` при
отсутствующих зависимостях.

Ожидаемый результат: APT разрешает альтернативы и устанавливает полный
server+contrib; прямой dpkg не маскирует отсутствие зависимостей и после
`apt -f install` пакет корректно донастраивается.

### Сквозные сценарии и критерии завершения

#### PT-E2E-01 — Существующий кластер → горячий архив → новая БД

Действия: из `SRC_CLUSTER/SRC_DB` создать горячий архив, восстановить его в
новую БД другого тестового кластера и сравнить контрольный набор.

Ожидаемый результат: данные, sequence, объекты, владельцы, роли, ACL и расширения
совпадают; источник не изменён.

#### PT-E2E-02 — Существующий кластер → холодный архив → удаление → рестори

Действия: создать холодный архив копии исходного кластера, удалить копию,
восстановить под другим именем/портом и в другом data-root.

Ожидаемый результат: восстановлены все БД, конфигурация и служба; контрольные
суммы совпадают; исходный кластер и общие логи не повреждены.

#### PT-E2E-03 — Горячий архив → DEB mode 4 → чистая система

Действия: собрать неинтерактивный mode 4 из горячего архива, установить на
чистом снимке с доступной более новой версией Postgres Pro и занятым портом.

Ожидаемый результат: APT выбирает самый новый допустимый server+contrib, кластер
создаётся на свободном порту, БД полностью восстановлена, финальное уведомление
о порте видно после `pg_restore`, пакет имеет состояние `installed`.

#### PT-E2E-04 — Холодный архив → DEB mode 3 → чистая система

Действия: собрать mode 3 из холодного архива и установить на чистом снимке.

Ожидаемый результат: используется точная физическая версия архива; кластер и
все БД восстановлены; повторная настройка пакета идемпотентна.

#### PT-E2E-05 — Плановый бэкап и ротация

Действия: выполнить созданную cron-команду несколько раз с тестовым малым
лимитом и затем восстановить самый новый оставшийся архив.

Ожидаемый результат: лимит соблюдён только для целевой маски; минимум один архив
сохранён; самый новый архив исправен и полностью восстанавливается.

Полное тестирование считается успешным только если:

1. Все обязательные пункты имеют состояние `PASS`.
2. Для каждого `BLOCKED`/`SKIPPED` есть утверждённое обоснование и оценка риска.
3. Нет зависаний, неожиданных интерактивных запросов в автоматическом режиме,
   необработанных трассировок Bash и ненулевых кодов при заявленном успехе.
4. После очистки на стенде остаются исходный кластер и исходные данные, а все
   временные кластеры, БД, cron-файлы, маркеры и тестовые каталоги перечислены в
   журнале как удалённые либо намеренно сохранённые.
5. К журналу приложены полные логи, контрольные суммы и пути всех использованных
   горячих/холодных архивов и DEB-пакетов.
