Доказательства: `tmp/release-2.4.2/<WSL>/fixtures/check.log`. Реальные кластеры эти проверки не изменяют.

## Регрессия удаления, включённая в 2.4.0 (2026-09-12)

`pg_dropcluster` заменён общей процедурой для PostgreSQL/Postgres Pro/Tantor. Точечная живая регрессия прошла на семи WSL: PostgreSQL-совместимые серверы 13, 16, 17, 18; Postgres Pro Enterprise, Tantor Free, SE и BE. На каждом создано и удалено два пустых QA-кластера: online в стандартном каталоге семейства и down в отдельном `/DATA/pgcc-delete-*`. Проверены отсутствие данных, конфигурации, unit, выбранного журнала, syslog-конфига и записи в реестре; исходные кластеры и SHA системного конфига сохранены. Версия старого установленного пакета не менялась: тестировались функции рабочей копии.

Helpers: `tools/prx-test-cluster-delete.sh REPO` (изолированные отрицательные проверки; повторно использован и перенесён из tmp/save), `tmp/save/test-cluster-delete-live.sh REPO DISTRO VERSION PORT DEFAULT_DATA_ROOT` (живые пустые QA-кластеры). Финальная повторная проверка: `tmp/delete-regression-20260912-final/<WSL>/live.log` и `isolated.log`; во всех семи WSL 14 удалений — PASS. В live.log записан SHA-256 проверенного сценария. Изолированно проверены stop/status failure/timeout, active unit/MainPID, недоступный реестр, общий/вложенный data-dir, mount, сохранность соседних файлов, внешней цели WAL, симлинка и общего журнала. Ранние попытки сохранены отдельно в `tmp/delete-regression-20260912/`.

Первоначальная подготовка QA на Astra 1.6/1.7 наткнулась на `stats_temp_directory` из старого `pg_createcluster`; исправлен только тестовый fixture (собственный createclusterconf, удаление устаревшей настройки в созданных QA-конфигах), затем прогон повторён. На Astra 1.8.6 `systemctl enable` возвращал разрыв соединения D-Bus; тестовая ссылка автозапуска создана напрямую. Само удаление не вызывает ни `systemctl disable`, ни `pg_dropcluster`, ни `syslog-ng-ctl reload`: удаляются точные ссылки, затем выполняется ограниченный по времени daemon-reload. Ранние неуспешные попытки подготовки сохранены в live.log.

Это проверка исправления удаления до изменения номера версии, не новый полный passed-прогон. Результаты прежнего полного прогона 2.3.5 не подменяют проверку 2.4.0. Внешние WAL/tablespace, пользовательские stats/socket-каталоги и нестандартные журналы не очищаются рекурсивно. Vanilla PostgreSQL отдельно живым тестом не проверялся; версии вне указанной матрицы не объявляются испытанными.

- формирование нового unit с изменёнными именем кластера, каталогом данных и PID-файлом для старого архива без unit.

Файлы реального кластера и содержимое старого архива при этой проверке не изменялись.

Дополнительно выполнен реальный интерактивный проход со старым архивом `16-subsys-20260905-085245.tar.gz`: конфликтующее имя `asvd` отклонено из-за существующего `/etc/postgresql/16/asvd`, после чего принято свободное имя `codex_restore_unused`. Операция отменена на итоговом подтверждении, поэтому архив не распаковывался и кластер не создавался.

Проверено обновление `external_pid_file` с исходного имени на целевое. В первом проблемном запуске PostgreSQL был `online`, но unit оставался `activating`, поскольку ожидал `/run/postgresql/16-subsys2.pid`, а сервер создавал `/run/postgresql/16-subsys.pid`.

При повторной проверке обычный `pg_ctlcluster 16 subsys2 start` от root зависал на перенаправлении в systemd, находившийся в состоянии `starting`. Прямой запуск `pg_ctlcluster --skip-systemctl-redirect 16 subsys2 start` завершился успешно: кластер перешёл в `online` и начал принимать подключения на порту `54322`. Для WSL сценарий переведён на этот режим; на штатной Astra Linux сохраняется совместная проверка кластера и systemd unit.

### Журнал и критерии зачёта

Журнал: **`TEST-X.Y.Z-journal.md`**, где версия соответствует проверенным
байтам. Указать SHA трёх .sh, DEB, git HEAD и dirty state. Для каждой ячейки
матрицы и каждого ID ниже записать полное имя, ожидаемый/фактический результат,
команду и ввод, начало/конец, rc, ссылки на логи/эталоны и результат очистки.

- PASS — выполнены все условия точки.
- FAIL — любое расхождение, зависание, необработанная ошибка или ложный успех.
- BLOCKED — нет предусловия/зависимости либо зависимый шаг не выполнен.
- SKIPPED — только явно согласованное исключение с причиной; это не PASS.

Общий лог команды разрешено использовать у нескольких ID; после каждой
контрольной точки приложить состояние кластеров/относящихся служб, перечень
артефактов и сравнение конфигов либо ссылку на тот же неизменившийся замер.
apt/dpkg/pg_dump/pg_restore stdout/stderr сохранять полностью, с маскированием
паролей и хешей. Отдельно отмечать ошибки обвязки, исправления и повторные
попытки — не перезаписывать неуспешные логи успешными.

Имена старых ID в таблицах обеспечивают связь с прежними журналами. Текст
«Действия и условия PASS» — обязательный чек-лист, не список примеров.
Для всей точки нужен каждый вариант; общее число запусков не заменяет матрицу.

### S10 — Финальная сверка, очистка и решение о passed

1. Проверить исходные кластеры/данные/состояния, конфиги и соседние логи против baseline. Не восстанавливать старые конфиги поверх обнаруженных параллельных пользовательских изменений: остановиться и зафиксировать расхождение.
2. Удалить только QA-объекты прогона: кластеры/БД, конкретные data/config/unit/ссылки, cron, собственные маркеры и пустые тестовые корни. Вернуть пакет/конфиг в согласованное исходное или целевое состояние; проверить dpkg --audit. Не удалять общие родительские каталоги.
3. Перечислить намеренно сохранённые архивы/DEB/копии конфигов/диагностику с путями, SHA и правами; подтвердить отсутствие оставшихся QA-процессов. Не публиковать секреты. Реальное удаление повторно не выполнять ради второго ID, если его условия уже доказаны.
4. Свести результаты всех 57 контрольных точек и очистки по матрице. Не считать общим PASS частичный успех S01–S09, исправление тестового fixture или успешный обход дефекта.
5. Переименовать журнал в **`TEST-X.Y.Z-journal-passed.md`** только при PASS всех обязательных условий и S10, без FAIL/BLOCKED/SKIPPED. Любые незавершённые/исключённые обязательные проверки оставляют журнал без passed; обоснование не подменяет выполнение. Исторические passed-журналы не изменять.
