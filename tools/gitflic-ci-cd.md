# Подключение Shell-агента к проекту GitFlic

Инструкция для GitFlic / Runner **4.5.0**. Текущий хост —
`a186-ci-cd` (`172.16.16.225`), Astra 1.8.6.39, OpenJDK 17. Агент выполняет только проверку синтаксиса,
сборку DEB и проверку его состава, без установки пакета и операций с кластерами.
Описание конвейера: [CI.md](../CI.md).

## 1. Выбрать проект и экземпляр агента

Агент должен быть зарегистрирован для **целевого проекта**. Тег `pgcc-deb`
выбирает подходящий агент, но сам по себе не предоставляет доступ к проекту.

13.09.2026 два независимых экземпляра перенесены с WSL
`alse-1.8.5-mg16.3.0` на `a186-ci-cd`:

| Назначение | Основной проект | Временная проверка CI |
| --- | --- | --- |
| Проект | `lesav/pg_claster_creator` | `lesav/pg_claster_creator-ci-test-20260913` |
| Имя агента | `pgcc-shell-a186-ci-cd` | `pgcc-ci-test-a186-ci-cd` |
| Служба | `gitflic-runner.service` | `gitflic-runner-ci-test.service` |
| Конфиг | `/etc/gitflic-runner/application.properties` | `/etc/gitflic-runner/ci-test.properties` |
| Рабочий каталог | `/var/lib/gitflic-runner` | `/var/lib/gitflic-runner-ci-test` |

Исполняемые файлы общие: `/opt/gitflic-runner/runner.jar`, `helper.jar`,
`helper.sh`. Учётная запись — `gitflic-runner`, без sudo.

**Если нужный экземпляр уже зарегистрирован, повторная регистрация не нужна:**
перейдите к запуску службы и проверке в разделе 5. При переносе сохранены
регистрации и привязки проектов; имена агентов обновлены в GitFlic, тег
`pgcc-deb` сохранён. Оба экземпляра активны; основной включён в автозапуск,
временный запускается вручную. Выполнение заданий без тегов отключено у обоих.
Сборка job №12 во временном проекте выполнена на новом хосте успешно,
включая передачу артефактов. Службы, файлы и отдельная учётная запись агента
удалены с WSL; общие зависимости и PostgreSQL не удалялись.

Для нового проекта не перезаписывайте конфиг основного агента: создайте отдельную
регистрацию, конфиг, рабочий каталог и службу по образцу временного экземпляра.
Приведённые пути и имена — примеры текущего стенда, при переносе их нужно изменить.

## 2. Проверить Linux и сеть

На Linux-хосте нужны Bash, Git, Python 3, Java совместимой с Runner версии,
`fakeroot`, `dpkg-deb`, `ar` (binutils), GNU tar, gzip, coreutils и findutils.
Для другой версии GitFlic сначала сверить совместимость Runner и Java
с документацией поставщика. Не обновлять рабочий агент вслепую.

```bash
java -version
git --version
command -v bash python3 fakeroot dpkg-deb ar tar gzip sha256sum
getent hosts gf.icd.nikiet.ru
curl --connect-timeout 5 --max-time 15 -I http://gf.icd.nikiet.ru/
```

Shell-агент сам устанавливает исходящее соединение с GitFlic: серверу не нужен
входящий доступ к агенту. При использовании WSL проброс портов не требуется. С хоста должны
быть доступны DNS, адрес GitFlic, Git HTTP/SSH по выбранному способу клонирования
и API/артефакты. HTTP не шифрует токены; при наличии HTTPS использовать его.

Сборочные каталоги должны находиться на Linux-ФС, не под `/mnt/d`. Не запускать
на этом агенте разрушительную программу тестирования PostgreSQL.

## 3. Получить токен регистрации проекта

1. Открыть **нужный проект → Настройки → Агенты CI/CD**.
2. Найти раздел регистрации нового агента и скопировать токен этого проекта.
3. Выбрать тип **Shell**, уникальное имя агента и тег **`pgcc-deb`**.
4. Для агента отключить выполнение заданий без тегов; для начала использовать
   одновременное выполнение одного задания.

Не путать четыре вида учётных данных:

- **Токен регистрации** нужен при подключении нового агента.
- **Сгенерированный конфиг агента** содержит его постоянные учётные данные.
- **`CI_JOB_TOKEN`** предоставляется конкретному заданию автоматически и
  остаётся под управлением Runner. Publisher его не использует и не изменяет.
- **`GITFLIC_RELEASE_TOKEN`** — пользовательский API-токен для publisher-а,
  отдельная секретная переменная CI. Без неё публикация завершается до обращения
  к API, без подстановки `CI_JOB_TOKEN`.

Не помещать токены, конфиги агента и регистрационные логи в Git, Markdown,
артефакты или переписку. Не включать `set -x` при работе с секретами.

### Настроить секрет публикации

В настройках переменных CI **целевого проекта** добавить `GITFLIC_RELEASE_TOKEN`
как секретную/маскируемую переменную. Значение пользователь вводит непосредственно
в GitFlic, не в YAML и не в аргументы команды. Пустую переменную-заглушку в YAML
не добавлять. Пользователь токена должен иметь доступ к проекту, API-права
`PROJECT_READ`, `PROJECT_WRITE`, право `MANAGE_RELEASE` и, для запуска конвейеров,
`EXECUTE_CI_CD`. Предпочтительны отдельная служебная учётная запись и срок действия.

Ограничить доступ секрета доверенными релизными ссылками/заданиями доступными
средствами данной установки. Маскирование не запрещает коду задания читать
переменную: секрет нельзя выдавать недоверенным веткам и форкам. Сборке и
локальным тестам publisher-а токен не нужен. Настройка секрета — отдельный шаг;
наличие имени переменной в документации не означает, что секрет уже сохранён.

## 4. Зарегистрировать новый экземпляр

Этот раздел нужен только для **новой** регистрации. Использовать официальный
дистрибутив Runner, соответствующий серверу. В проверенном варианте это
[Runner 4.5.0](https://gitflic.ru/project/gitflic/runner/release/32668765-c381-411a-8091-210afeacb925).
`runner.jar`, `helper.jar` и `helper.sh` устанавливаются вместе, под владельцем
root; рабочие каталоги принадлежат непривилегированной учётной записи агента.

Проверенный helper регистрации уже существует в каталоге подготовки миграции:
`D:/Ai/pg_claster_creator.new/tools/prx-register-gitflic-runner.sh`.
Это **внешний helper**, не файл `tools/` внутри данного Git-репозитория.
Если он доступен, сначала прочитать его header и переиспользовать:

```text
prx-register-gitflic-runner.sh WORKDIR JAR URL NAME TAGS TEMPLATE
```

Токен передаётся helper-у через stdin. WORKDIR должен быть отдельным приватным
каталогом регистрации; helper не перезаписывает существующую регистрацию.
Создаваемый лог также содержит потенциально чувствительные данные.

Если helper отсутствует, эквивалентная команда Runner приведена ниже. Выполнять
её в отдельной root-сессии без трассировки, из нового каталога регистрации
с правами `0700`. Файл `runner-default.properties` подготовить заранее:

```properties
runner.executor=shell
runner.workingDir=/var/lib/gitflic-runner-ci-test
runner.helperDir=/opt/gitflic-runner
runner.runnerConcurrencyMode=DEFAULT
runner.enableExecScriptsInSession=true
logging.file.name=/var/lib/gitflic-runner-ci-test/log/server.log
logging.level.root=INFO
```

```bash
umask 077
read -r -s -p 'Project registration token: ' pgcc_registration_token
printf '\n'
timeout 60 java -jar /opt/gitflic-runner/runner.jar register \
  --url http://gf.icd.nikiet.ru \
  --token "$pgcc_registration_token" \
  --name pgcc-ci-test-a186-ci-cd --tags pgcc-deb \
  --default-config ./runner-default.properties >registration.log 2>&1
pgcc_registration_rc=$?
unset pgcc_registration_token
printf 'Registration exit code: %s\n' "$pgcc_registration_rc"
```

Runner 4.5 принимает токен аргументом, поэтому на время регистрации его может
видеть привилегированный наблюдатель процессов. Чтение через `read -s` не
записывает значение в историю команд, но не устраняет это ограничение Runner.

При ненулевом коде изучить приватный лог, не повторять регистрацию вслепую.
При успехе появится `config/application.properties`. Перенести **именно его**
в выбранный постоянный конфиг, задать владельца `root:gitflic-runner` и `0640`.
Рабочий каталог и `log/` создать с владельцем `gitflic-runner` и правами `0750`.
После проверки установленного конфига удалить только временные копии секретов
и регистрационный лог. Постоянный конфиг не удалять.

## 5. Запустить службу и проверить подключение

Для нового экземпляра создать отдельную systemd-службу. Пример временного агента:

```ini
[Unit]
Description=GitFlic project Shell runner
After=network-online.target

[Service]
User=gitflic-runner
Group=gitflic-runner
WorkingDirectory=/var/lib/gitflic-runner-ci-test
Environment=HOME=/var/lib/gitflic-runner-ci-test
Environment=PATH=/usr/local/bin:/usr/bin:/bin
Environment=LANG=C.UTF-8
ExecStart=/usr/bin/java -Xms128m -Xmx1024m -jar /opt/gitflic-runner/runner.jar start --config=/etc/gitflic-runner/ci-test.properties
Restart=on-failure
RestartSec=10
TimeoutStopSec=45
UMask=0027
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ProtectHome=true
InaccessiblePaths=-/mnt -/etc/postgresql -/.postgres -/DATA -/BACKUP

[Install]
WantedBy=multi-user.target
```

Сохранить как `/etc/systemd/system/gitflic-runner-ci-test.service`; не заменять
существующий unit без сравнения. Для нового/изменённого unit выполнить:

```bash
sudo systemctl daemon-reload
sudo systemctl start gitflic-runner-ci-test.service
sudo systemctl status gitflic-runner-ci-test.service --no-pager
sudo journalctl -u gitflic-runner-ci-test.service -n 50 --no-pager
```

В интерфейсе проекта проверить: агент активен, тип Shell, тег `pgcc-deb`,
задания без тегов отключены. Активная Linux-служба сама по себе ещё не доказывает
успешную связь с проектом. Прежде чем пересылать логи, удалить из них секреты.

`systemctl enable` нужен только при намерении запускать агент при каждой
загрузке Linux; для него требуется секция `[Install]`. У установленного ранее
временного unit этой секции нет: для возобновления проверки достаточно `start`.

Из Windows подключиться к текущему хосту и запустить временный экземпляр:

```powershell
ssh astra@172.16.16.225 "sudo systemctl start gitflic-runner-ci-test.service"
```

Для альтернативного размещения на WSL: автозапуск systemd-службы при загрузке WSL **не равен** автозапуску WSL при
входе в Windows. Windows должен оставаться включённым; сон, перезагрузка и
`wsl --shutdown` могут оборвать задание. Запуск WSL при входе в Windows
настраивается отдельно. Текущий агент на `a186-ci-cd` от WSL не зависит.

## 6. Подключить конвейер и принять результат

1. Убедиться, что в целевую ветку отправлен корневой `gitflic-ci.yaml` и
   необходимые helper-ы из `tools/`. В **Настройки → Настройки CI/CD** путь
   конфигурации — `gitflic-ci.yaml`.
2. В задании должен быть тег `pgcc-deb`, совпадающий с тегом агента.
3. Выполнить обычный push либо **CI/CD → Создать конвейер**, выбрав ветку.
4. Проверить успешное задание `build-deb`: синтаксис Bash, version/help,
   сборка mode 1, gzip, LICENSE, Markdown, MAN, конфиг, сценарии и их права.
5. На вкладке **Артефакты** проверить скачиваемый `artifact.tar.gz` со сроком
   хранения 30 дней. Внутри `dist/`: DEB, `SHA256SUMS`, `package-contents.txt`,
   `build.log`. После скачивания выполнить `sha256sum -c SHA256SUMS` из `dist/`.
6. В checkout команда `git ls-files -- dist` должна выдавать пустой результат.
   Успех сборки не является результатом полного функционального тестирования.

Если задание ожидает агента: проверить проектную регистрацию, активность службы,
совпадение тегов, доступность сети и отсутствие занятого слота. Если clone
работает, а сборка нет — смотреть лог задания, а не перерегистрировать агент.

## 7. Теги и публикация: известные ограничения

Подключение агента и обычная сборка **подтверждены**. Автоматическая публикация
релиза на `gf.icd.nikiet.ru` в проверке 13.09.2026 **не завершена**:

- Push `v2.5.4` не создал теговый конвейер автоматически. Запуск через кнопку
  CI на странице тега создал правильный контекст и задания build/publish.
- Пробный `NEW_TAG`-скрипт через `pipelineService.create` создавал branch-контекст
  как с полной, так и с короткой ссылкой. Он отключён; не копировать этот
  обходной путь как рабочую автоматизацию.
- С `CI_JOB_TOKEN` чтение релизов вернуло HTTP 200, создание — HTTP 500
  (`InvalidDataAccessApiUsageException`).
- После ручного создания карточки релиза повтор публикации получил HTTP 415.
  Уточнённая причина: сервер определяет DEB как `application/x-debian-package`
  и отклоняет этот тип. Формат multipart соответствует документации; изменение
  объявленного Content-Type не устраняет серверную проверку содержимого.
- Документированный REST-запуск `/cicd/pipeline/start` с
  `{"refName":"v2.5.4","isTag":true}` и `CI_JOB_TOKEN` вернул HTTP 403
  (`AccessDeniedException`). Теговый конвейер не создан.

### Оставшиеся действия

1. Получить исправленную серверную сборку с поддержкой DEB
   (`application/x-debian-package`) и согласовать поддержку файлов контрольных
   сумм, не отключая проверку типов. Ручная правка JAR на проде не рекомендуется.
2. Настроить `GITFLIC_RELEASE_TOKEN` и проверить обновлённый publisher в CI.
   Перезапуск старого тега `v2.5.4` выполняет старый код publisher-а: правки
   рабочего дерева туда не попадут. Не передвигать тег ради проверки.
3. Отдельно завершить автозапуск при push тега. Успешный REST-запуск с
   пользовательским токеном не подтверждает автоматическую обработку push.

Не выдавать агенту root/sudo и не отключать его защиту для устранения HTTP-ошибок.
`CI_JOB_TOKEN` и токен регистрации агента не подменять пользовательским токеном:
publisher читает исключительно отдельную `GITFLIC_RELEASE_TOKEN`.

Контракты запросов сверены с документацией:
[релизы](https://docs.gitflic.ru/latest/api/release/) и
[CI/CD](https://docs.gitflic.ru/latest/api/cicd/). Документация latest не доказывает
наличие исправлений в установленной версии 4.5.0; окончательная проверка — на сервере.

После исправления API проверить полный путь: тег совпадает с версией → сборка
успешна → релиз указывает на нужный коммит → DEB и SHA256SUMS прикреплены →
скачанные файлы совпадают по SHA-256. Только тогда считать автопубликацию готовой.

## 8. Завершить временную проверку

```bash
sudo systemctl stop gitflic-runner-ci-test.service
sudo systemctl show gitflic-runner-ci-test.service -p ActiveState -p MainPID -p Result
```

Сохранить журнал проверки и необходимые артефакты до окончания срока хранения.
Не удалять основной агент, его конфиг, исходный проект или действующие релизные
теги. Удаление временного проекта/регистрации — отдельное действие после
согласования; остановки службы достаточно, чтобы она не брала новые задания.
